# API Contract

This document describes the initial logical API. Exact schemas and authentication requirements will be finalized during implementation.

## Conventions

- JSON is used for metadata and calculation requests.
- Multipart upload is used for source files.
- IDs are opaque values generated by the backend.
- Timestamps use UTC.
- Errors return `{"detail": "<human-readable message>"}` with a conventional HTTP status code (`400`/`404`/`409`/`413`/`422`, etc.); there is no separate machine-readable error-code field. An unhandled server error additionally returns a `request_id` in the body and an `X-Request-ID` response header, for matching against server logs.
- CORS allowed origins default to `localhost:3000/3001/3002` and are configurable via the `CORS_ALLOWED_ORIGINS` environment variable (comma-separated).

## Health

### `GET /health`

Returns application and dependency status.

## Authentication and Users

- `POST /auth/login` - log in with `{"email": ..., "password": ...}`, sets an httpOnly session cookie
- `POST /auth/logout` - revoke the current session
- `GET /auth/me` - the logged-in user
- `POST /users` / `GET /users` / `PATCH /users/{user_id}` / `DELETE /users/{user_id}` - user management (admin only, scoped to the caller's own tenant — see below)
- `GET /users/lookup?username=` - exact-username lookup, scoped to the caller's own tenant (any authenticated caller, not just admins)
- `POST /tenants` / `GET /tenants` - create/list tenants (`platform_admin` only; PLAN.md Phase 16)

Every route below requires a logged-in session, and most are further
scoped to a role and/or project ownership/membership — see
DECISIONS.md ADR-009 and PLAN.md Phase 15 for the full matrix. A
caller who isn't a member of a given project gets `404` (not `403`)
so a project's existence isn't leaked to someone unauthorized to see it.

A `platform_admin` role sits above `admin` (PLAN.md Phase 16, DECISIONS.md
ADR-010): `admin` sees/manages projects, clients, and users within its own
tenant only, not the whole install; `platform_admin` crosses every tenant.
Every list/read endpoint below that says "admin sees all" means "within its
own tenant" for `admin`, and genuinely all of them for `platform_admin`. A
resource outside the caller's tenant is `404`, the same don't-leak-existence
treatment as an unauthorized project. Creating a project, client, or user
assigns the caller's own tenant automatically; a `platform_admin` caller may
instead name an existing tenant explicitly via `tenant_id` in the request
body, naming a tenant created via `POST /tenants` (2026-09-20 — previously
only creatable by direct database access).

Login is by `email`, not `username` (2026-09-20, PLAN.md Phase 16):
`username` is unique only per tenant, so a bare `username` lookup can't say
which tenant's "jsmith" is meant, while `email` is unique install-wide.
`POST /users` requires `email` in the body alongside `username`/`password`/
`role`; `PATCH /users/{user_id}` accepts an optional `email`. `email` is
lowercased on write and returned on `UserResponse`. This is enforced
app-side, plus (2026-09-20) Postgres Row-Level Security on `projects`,
`clients`, and every table nested under a project (`0021_add_row_level_security`,
`0022_extend_rls_nested_tables`) as a database-enforced backstop for the
shared-instance case — **verified end-to-end against a real local Postgres
18 instance (2026-09-20)**; see RISK_REGISTER.md and those migrations'
docstrings.

## Clients

- `POST /clients` - create a client (admin/power_user)
- `GET /clients` - list clients (scoped to the caller's own tenant; platform_admin sees all)
- `GET /clients/{client_id}` - retrieve a client (scoped to the caller's own tenant)
- `PATCH /clients/{client_id}` - update a client (admin/power_user, own tenant)
- `POST /clients/{client_id}/archive` - archive a client (admin/power_user)

## Projects

- `POST /projects` - create a project (admin/power_user; a power_user caller auto-becomes owner)
- `GET /projects` - list projects (admin sees all within its own tenant; platform_admin sees all across every tenant; everyone else sees only projects they own or are a member of)
- `GET /projects/{project_id}` - retrieve a project
- `PATCH /projects/{project_id}` - update a project
- `POST /projects/{project_id}/archive` - archive a project (owner/admin only)
- `GET /admin/projects/archived` - list archived projects (not `user` role)
- `POST /admin/projects/{project_id}/restore` - restore an archived project (owner/admin only)
- `DELETE /admin/projects/{project_id}` - permanently purge an archived project (owner/admin only; deletes its database rows, cascading to files, jobs, revisions, entities, calculations, summaries, and Q&A history, and its on-disk storage directory)
- `GET /projects/{project_id}/members` - list a project's collaborators
- `POST /projects/{project_id}/members` / `DELETE /projects/{project_id}/members/{user_id}` - add/remove a collaborator (owner/admin only; the collaborator must belong to the project's own tenant)
- `PATCH /projects/{project_id}/owner` - reassign the project's owner (owner/admin only; the new owner must be a power_user in the project's own tenant)

A project's optional `coordinate_reference_system` must be a projected CRS. `POST`/`PATCH` return `422` for a geographic (lat/lon degree) one, such as `EPSG:4326`, because every measurement the app performs is planar. A CRS that pyproj does not recognize, or none at all, is accepted and the project's coordinates are assumed to be planar already.

## Files and Processing

- `POST /projects/{project_id}/files` - upload a source file
- `GET /projects/{project_id}/files` - list source files
- `GET /projects/{project_id}/files/{file_id}/download` - download a permitted file
- `DELETE /projects/{project_id}/files/{file_id}` - archive a source file and hide it from normal listings
- `GET /admin/files/archived` - list archived files
- `POST /admin/files/{file_id}/restore` - restore an archived file
- `DELETE /admin/files/{file_id}` - permanently purge an archived file
- `POST /projects/{project_id}/files/{file_id}/process` - start or retry processing
- `POST /projects/{project_id}/files/{file_id}/replace` - upload a new version of an existing file
- `GET /projects/{project_id}/files/{file_id}/extraction` - retrieve the latest normalized extraction
- `GET /projects/{project_id}/processing` - list processing jobs
- `GET /projects/{project_id}/processing/{job_id}` - retrieve job status and warnings

Supported upload extensions are `.pdf`, `.dxf`, `.csv`, `.txt`, `.tif`, `.tiff`, and `.xml` (LandXML). Uploads are limited to 50 MB, stored under the configured local storage path, and identified by a SHA-256 checksum. A duplicate checksum within the same project returns `409`, including archived records. Delete archives the physical file and preserves metadata, revisions, and calculations. Processing currently runs synchronously and records `processing`, `completed`, or `failed` status. TIFF/TIF processing records raster metadata and reports that OCR is not enabled; asynchronous execution remains a later optimization.

`replace` uploads a new file linked to the target's `document_group_id` (marking the target as superseded via `superseded_by_id`), recording it as an explicit new version of the same document rather than an unrelated file that happens to share a name. Replacing an archived file, or a file that has already been replaced, returns `409`.

## Site Model

- `POST /projects/{project_id}/site-model/revisions/from-extraction/{file_id}` - accept an extraction into a site-model revision
- `GET /projects/{project_id}/site-model/revisions` - list site-model revisions
- `GET /projects/{project_id}/site-model/revisions/{revision_id}/entities` - list revision entities
- `GET /projects/{project_id}/site-model/revisions/{revision_id}/compare/{other_revision_id}` - compare revisions
- `GET /projects/{project_id}/site-model/entities/{entity_id}/snippet` - render the entity's source DXF as an SVG with that entity highlighted (DXF-sourced entities only; other file types return `400`)

There is no route for a bare "active revision" or unscoped entity list; entities are always read through a specific revision.

## Calculations

- `POST /projects/{project_id}/calculations` - run a calculation
- `GET /projects/{project_id}/calculations` - list calculations
- `GET /projects/{project_id}/calculations/{calculation_id}` - retrieve a calculation

`POST` accepts a calculation type, input entity IDs or explicit points, units, and optional revision ID. Returns the formula, normalized inputs, result, unit, assumptions, and source references.

`distance`, `area`, and `perimeter` return `400` if the project's `coordinate_reference_system` is geographic — those formulas are Euclidean and would report degrees under a linear unit label. `slope` and `elevation` are unaffected, since they work on supplied values rather than coordinate positions. The same rule applies to questions: a question needing a planar measurement returns the standard insufficient-data answer naming the CRS, and a site summary of such a project carries a matching attention flag.

Area and perimeter also accept native Circle JSON, for example `{"type":"Circle","center":[100,200],"radius":25}`. The radius uses `coordinate_unit`; area uses `pi * radius^2` and perimeter uses `2 * pi * radius`.

Initial calculation types:

- `distance`
- `elevation`
- `slope`
- `area`
- `perimeter`

Geometry calculation requests include both `coordinate_unit` and output `unit`. For example, coordinates `[10,0]` and `[5,0]` with both values set to `ft` produce `5 ft`; with both set to `m`, they produce `5 m` (or `16.404 ft` when output is `ft`). Calculation responses include normalized inputs, formula, result, unit, assumptions, source entity IDs, and optional revision ID. Elevation requests return average result plus minimum, maximum, average, and count details.

## Summaries and Questions

- `POST /projects/{project_id}/summaries` - generate a site summary
- `GET /projects/{project_id}/summaries` - list past summaries, most recent first
- `POST /projects/{project_id}/questions` - ask a source-grounded question

Both accept an optional `revision_ids` list (query params for `summaries`, a JSON body field for `questions`) naming which revisions to draw on. When omitted, it resolves to the project-boundary default: the single latest revision for each distinct document lineage (`SourceFile.document_group_id`) across the whole project, so a superseded (replaced) file's older revision is excluded automatically. The response's `revision_ids` records exactly what was resolved, for provenance.

Summaries are persisted server-side and listable (above). There is no list route for past questions; the frontend keeps question/answer history in local state as it's created within a session.

The current implementation uses a deterministic mock provider. Unsupported questions return insufficient-data responses rather than invented engineering facts.

Recognized question intents (`route_question` in `ai_service.py`), each resolved deterministically from the extracted site model rather than generated: `directional_distance`, `distance`/`setback`, `slope`, `elevation`, `elevation_lookup` (a specific labeled spot elevation, e.g. "EL 102.5", or the difference between two), `perimeter`, `area`, `dimensions`/`orientation` (a polygon's width/length/compass-axis orientation via its minimum-area oriented bounding rectangle), `setback_compliance` (a building's clearance from its parcel boundary, compared against an explicit numeric setback in the question if one is given), `count` (how many entities carry a given role), `drainage`/`utility` (keyword-matched entity presence), and a `summary` fallback that retrieves relevant extracted text. Role-aware intents (`area`, `perimeter`, `dimensions`, `orientation`, `setback_compliance`, `count`, `directional_distance`) recognize `parcel_boundary`/`building_footprint`/`driveway_road`/`curb_cut`/`utility_easement`/`parking`/`tree`/`sidewalk`/`detention_basin` role phrases (PLAN.md Phase 14); a question naming no role considers every candidate of the right geometry type, which is ambiguous rather than answered once more than one exists.

## Kinds of Error Condition

These are not literal error codes (see Conventions above) — just the situations the API distinguishes, and how each currently surfaces:

- Invalid request body / unsupported file type / not found → `400`/`404` with a descriptive `detail` message
- Duplicate file checksum within a project → `409`
- Request body too large → `413`
- Malformed or unsupported geometry in a calculation request → `400` with a descriptive `detail` message
- A plan-sheet snippet entity that can't be found in its source DXF (e.g. a stale index) → `422`
- Processing failure → not an HTTP error; the source file's `status` becomes `failed` with `error_message` set, retrievable via the file/processing endpoints
- Insufficient data to answer a question → not an HTTP error; a `200` response whose `answer.confidence` is `0.0` and whose text says so explicitly, rather than an invented result
- Unhandled server error → `500` with `{"detail": "Internal server error", "request_id": ...}` and a matching `X-Request-ID` header

## API Rules

- Never expose arbitrary filesystem paths.
- Validate project ownership before accessing project data.
- Limit upload size and accepted media types.
- Return warnings when extraction is incomplete.
- Do not return an AI-generated measurement without source context or a clearly stated limitation.
