- Source-file download, deletion, and queued processing-job API workflows.
- Project/file workspace UI and PostgreSQL-backed Phase 2 smoke-test coverage.
- Normalized TXT, CSV, PDF, and DXF extraction with source references and warnings.
- Versioned extracted-document storage and completed/failed processing statuses.
- TIFF/TIF upload support with raster metadata extraction; OCR remains deferred.
- Initial site-model revisions with Shapely validation, PyProj transformation support, and read APIs.
- Deterministic distance, area, perimeter, and slope calculations with persisted provenance.
- Phase 6 workspace controls for file deletion, site-model revision inspection, and calculation forms/results.
- Explicit geometry coordinate units for calculations, preventing unintended meter-to-feet conversion.
- Native Circle geometry support for area and perimeter calculations.
- Phase 6 idempotent revision acceptance and soft-delete file archiving with in-app confirmation.
- Phase 6 admin archive restore/purge, revision comparison, elevation statistics, and geometry preview.
- Phase 7 deterministic/mock source-grounded summaries and question-answer persistence.
- CSV site-model acceptance now aggregates non-geometric table rows and maps coordinate rows to points instead of creating one unmapped entity per row.
- TXT site-model acceptance now aggregates text lines into one text entity with line count and sample lines.
- Phase 7 grading, drainage, and utilities summary sections, plus attention flags for steep slopes, tight clearances, unusual elevation ranges, and unmapped entities.
- Deterministic distance, slope, and elevation question answering from site-model geometry, with clear ambiguous/insufficient-data responses when the required entities are not present or not uniquely identifiable.
- Source-text retrieval for explanatory answers, with prompt-injection sanitization applied to extracted document text before use.
- Phase 6 calculation-to-geometry highlighting: selecting a calculation result highlights the site-model geometry it references (switching revisions if needed) or explains when a calculation type has no associated geometry.
- Playwright browser tests covering upload, calculation, and error states, run via `npm run test:e2e`.
- Fixed `createProject`, `uploadFile`, and `createCalculation` leaving the UI permanently disabled after a network failure by adding the same try/catch/finally handling already used elsewhere; the project-creation status message now renders even before a project is selected.
- Phase 8 request correlation IDs (`X-Request-ID`), structured request logging, and a JSON error response with request id for unhandled exceptions instead of a bare "Internal Server Error" body.
- Phase 8 request-body size limit (2 MB) for non-upload endpoints, and a `/health` database-connectivity check.
- Fixed a race condition where concurrent uploads of the same file content could all succeed instead of only the first: added a database-level unique constraint on (project, checksum) and a matching migration, with the duplicate-upload response now also covering the concurrent case.
- Added a "Retry" action for files stuck in `failed` or `processing` status (e.g. after an interrupted server process), and surfaced the stored processing error message in the file list.
- Added unit tests for path-traversal and unsafe-filename rejection in local storage, and API-level tests for malformed-file processing, interrupted-job recovery, and concurrent duplicate uploads.
- Added a "Site intelligence" workspace section: a "Request site summary" action and an "Ask a question" form, closing the gap where Phase 7's summary/question-answering API had no frontend UI. Answers and summaries are clearly labeled AI-generated with method, confidence, and limitations shown alongside the result.
- Formalized the no-authentication/single-user MVP decision as ADR-005 and updated the risk register to reflect Phase 7/8 mitigations (deterministic AI answers, the checksum race fix, and the request-body size limit); AI-provider timeout handling is explicitly deferred until a real network provider is integrated.
- Added real end-to-end Playwright coverage (create project, upload, process, inspect, calculate, select-to-highlight, ask, and request-summary) running against a live backend with an isolated SQLite database and storage directory, in addition to the existing mocked component tests.
- Documented current known limitations and a test-results summary in VERIFY.md for the Phase 8 exit criteria.
- Completed Phase 8 with a non-licensed technical review of the calculation engine (VERIFY.md section 12): verified every formula against standard civil-engineering/geometry definitions and hand-verified test cases, added missing edge-case tests (downhill/level slope, negative elevations, zero distance, negative-input rejection), and logged a newly found risk that calculations assume a projected CRS with nothing yet enforcing it. A licensed PE review is still recommended before real engineering use.
- Re-planned PLAN.md's remaining phases after auditing Requirements.md against the shipped implementation: found seven capabilities from the original requirements (LandXML, label-to-geometry linking, key-phrase extraction, bearing/COGO parsing, semantic site-model classification, directional questions, and plan-sheet snippets) that were never explicitly built or explicitly deferred. Moved release/deployment work to a renamed Phase Z and inserted a new Phase 9 to close these gaps beforehand.
- Phase 9: added LandXML parsing (`.xml` uploads) to the extraction pipeline, using the standard library's XML parser (no new dependency). Extracts `CgPoints` and surface `Pnts`/`P` points, and straight `Line` segments from alignment `CoordGeom`; curved (`Curve`/`Spiral`) alignment segments are explicitly skipped with a warning rather than approximated, consistent with the project's rule against inventing geometry. Points and lines flow through the same site-model acceptance path as the other parsers.
- Phase 9: labels extracted with a location (currently DXF `TEXT` entities, e.g. "FF=102.50") are now linked to their nearest valid geometry entity when accepting a site-model revision. The link is stored on the label entity's properties as `linked_geometry` (target entity id, type, distance, and the target's own source reference) so it is traceable through the API. A label with nothing within 10 coordinate units is left unlinked rather than matched to unrelated geometry.
- Phase 9: narrative text parsing (`.txt` and PDF page text) now scans for a fixed vocabulary of civil-engineering key phrases (e.g. "setback", "finished floor elevation", "property line", "easement") and surfaces each match as its own searchable `key_phrase` site-model entity with the matched phrase and surrounding line as context, rather than only matching keywords reactively when a question is asked. Shown in the workspace's entity grid with the matched phrase in place of a source file name.
- Phase 9: CSV parsing now recognizes quadrant bearing/distance boundary courses (e.g. `N45.00E`, `100.00`) alongside a starting point of beginning (explicit x/y or easting/northing columns), chaining each course from the previous point into a `cogo_line` entity with derived line geometry, so a parcel boundary can be described either by raw coordinates or by bearing/distance courses in the same file.
- Phase 9: site-model entities now carry an optional `semantic_type` (parcel boundary, building footprint, driveway/road, curb cut) inferred from a DXF layer name or an explicit CSV type/classification column, plus an optional `zoning` tag passed through from a CSV zoning/zone column. Shown on the entity card in the workspace UI in place of the generic entity type badge.
- Phase 9: questions naming a compass direction and an entity role (e.g. "distance to the north property line") now resolve to a new `directional_distance` intent that picks the correctly-classified entity furthest in that direction (using the `semantic_type` from the previous Phase 9 item) and measures its distance to another mapped entity, rather than requiring exactly two mapped geometries and refusing as ambiguous whenever more exist.
- Phase 9 (final item): added a `GET /projects/{project_id}/site-model/entities/{entity_id}/snippet` endpoint that re-renders a DXF-sourced entity's source file to SVG with that entity highlighted in red, using ezdxf's built-in SVG drawing backend (no new dependency). Added a "View plan-sheet snippet" button in the workspace's site-model section, available whenever an entity is highlighted (via the entity grid or a selected calculation result), which fetches and displays the highlighted plan sheet inline. Scoped to DXF-sourced entities only, since PDF rasterization would require a new dependency; other file types return a clear 400 response rather than attempting an unsupported render. This closes the seventh and final Phase 9 item.
- Added Playwright end-to-end coverage for the three Phase 9 UI additions (key-phrase display, semantic-type badges, and plan-sheet snippets), run against the real backend like `full-workflow.spec.ts`: uploading a narrative `.txt` file shows the extracted key phrases as quoted entity cards, and uploading a DXF fixture with named layers shows the resulting "parcel boundary"/"building footprint" badges and produces a viewable plan-sheet snippet image.
- Fixed `NEXT_PUBLIC_API_URL` being silently ignored when set via the repo-root `.env` (Next.js only reads `.env` files from `frontend/`, not the repo root, so the documented `Copy-Item .env.example .env` setup step never actually reached the frontend). `frontend/next.config.ts` now reads it from the root `.env` as a fallback when it isn't already set as a real environment variable.
- Made the backend's CORS allowed origins configurable via a new `CORS_ALLOWED_ORIGINS` setting (comma-separated, defaults to the existing `localhost:3000/3001/3002`) instead of a hardcoded list, so the frontend can be run on a different port without every API request being silently blocked by CORS.
- Fixed the status message (shown after every upload, process, calculation, question, etc.) being rendered once at the very bottom of the page, below every workspace section, requiring a scroll to see it. It's now a sticky banner directly under the page header, staying visible regardless of scroll position for every action, not just upload.
- Removed the workspace's 1180px max-width cap so it fills the available viewport width instead of leaving empty margins on wider screens; there was no recorded reason for the cap, and the data-dense layout (entity grids, tables, forms) benefits from the extra room.
- Fixed `GET /projects/{project_id}/files` and `GET /projects/{project_id}/processing` returning rows in no defined order (no `ORDER BY` clause at all, so the order was whatever the database happened to return). Both now sort most-recent-first, matching the pattern already used by the calculations, revisions, and archived-files list endpoints.
- Processing warnings (already captured by the backend since Phase 3, e.g. "Page 1 contains no extractable text", skipped DXF entities, skipped LandXML curves) are now shown in the workspace UI for the first time. A completed file with warnings shows "Completed with warnings" instead of a plain "Processing completed", with the warning text(s) listed underneath (deduplicated and capped at 3 with a "+N more" summary, so a file with many warnings can't break the layout). Found and fixed while investigating a real LandXML processing failure that had no way to be diagnosed from the UI.
- Fixed three real LandXML gaps found via that investigation, using actual third-party LandXML files rather than only synthetic fixtures: (1) alignments defined via `AlignPIs` (a sequence of PI points with curve/spiral parameters, used by Ohio DOT-style road alignment exports) were not recognized at all, even for their straight tangent segments — now extracts PI points and straight PI-to-PI segments where neither endpoint has a curve/spiral, warning on the rest rather than approximating a curve as a straight line; (2) `pntRef`-based indirect point references (a point or `Line` `Start`/`End` referencing another point's coordinates by ID instead of repeating them inline, common in real parcel/survey exports) were silently ignored — now resolved from an index built over the whole document; (3) `<Parcel><CoordGeom>` boundary geometry (as opposed to `<Alignment><CoordGeom>`) was invisible to the parser entirely. Together these took a real Australian parcel/survey file from silently extracting 0 of its 1,196 boundary lines (while still reporting "completed") to extracting all of them, and turned two real road-alignment files from an outright processing failure into a successful, honestly-caveated extraction.
- Fixed LandXML coordinate parsing rejecting numbers written with a comma decimal separator (e.g. `3394639,42776972`, produced by German-locale CAD exports like Vestra Cad Civil), which previously caused every point in an otherwise well-formed file to fail parsing and the whole file to be rejected as having no supported geometry. Found via a real 92-point cross-section file that failed with "no supported CgPoints... found" despite containing valid points.
- Reworded the "Completed with warnings" processing status to "Processing completed with warnings" so it reads as a variant of "Processing completed" rather than an unrelated status. Upload status messages now name the file involved (e.g. "invoice.pdf uploaded and queued for processing") instead of a generic message, and a duplicate-content (409) upload rejection now names both the rejected file and the existing file it matches.
- Fixed a race condition in accepting site-model revisions: concurrent "Accept revision" requests for different files in the same project could both compute the same next revision number, producing two revisions with the same number in one project (confirmed already present in existing data — one project had `revision_number` 4 duplicated four times). Added a database-level unique constraint on `(project_id, revision_number)`, a migration that renumbers any existing duplicates first, retry-on-conflict handling in the accept endpoint, and a frontend guard so only one "Accept revision" can be in flight at a time.
- Added explicit file versioning: a file row now has a "Replace" action to upload a newer version of that same document (e.g. a corrected survey re-export), recorded via a shared `document_group_id` rather than guessed from the filename. A replaced file is marked "Replaced by a newer version" and can't be replaced again until its replacement is (avoiding a fork in the version history).
- Site summaries and questions now default to a "whole project" scope — the latest accepted revision of every uploaded document, aggregated together — instead of being limited to whichever single revision happened to be selected in the site-model viewer. A new "Scope" control lets a user instead pick one or more specific revisions. The project-boundary default automatically excludes a file's superseded (replaced) revision, using the file-versioning link above.
- Added `created_at` to `site_model_entities`, the one database table with no timestamp column at all (found during an audit of every table). Backfilled from the parent revision's `created_at` for all 634,394 existing rows.
- Phase 10 (project lifecycle, first half): a project can now be archived from the workspace UI with confirmation, listed in a new "Archived projects" admin panel alongside the existing archived-files panel (renamed from "Admin archive" to "Archived files" for consistency), restored, and permanently purged. Permanent purge deletes the project's database rows (cascading to its files, jobs, revisions, entities, calculations, summaries, and Q&A history) and its on-disk storage directory — mirroring the file lifecycle already shipped in Phase 6. Multi-file operations (the other half of Phase 10) remain open.
- Fixed permanently purging a project being impractically slow for a project with a large site model: it deleted every dependent row through the ORM one at a time (confirmed still running after over a minute against a real project with 537,000 entities, safely cancelled without any data loss since the whole operation was one transaction). Purge now issues a single `DELETE` and lets the database's own `ON DELETE CASCADE` foreign keys handle the rest, and a missing index on `site_model_entities.revision_id` (used by that cascade and by every entity lookup) has been added. A 100,000-entity purge now completes in about half a second. Also fixed the automated test suite silently not verifying cascading deletes at all, since SQLite doesn't enforce foreign keys unless a connection explicitly turns them on.
- Fixed a bug introduced in the `site_model_entities.created_at` migration: the column was added without an actual database-level default, only the ORM model's default metadata, so any new entity created since that migration would have failed outright. Found and fixed before it was hit by a real accept-revision call.
- Replaced the header's hardcoded "Phase 6 active" badge, a leftover label from development that had no connection to anything real, with a live API status indicator: "API connected · `<environment>`" (the backend's actual `APP_ENV` value, checked via `GET /health` on page load) or "API unreachable" if the backend can't be reached.
- Phase 10 (multi-file operations, second half): a project's file list now supports selecting multiple files (per-row checkboxes plus a "select all," respecting the current sort/filter) with batch "Process selected" and "Archive selected" actions, and the Archived files panel got the matching "Restore"/"Purge" batch actions. Every batch action reports partial success/failure by name (e.g. "1 of 2 file(s) archived. Failed: sr658.xml (File is already archived)") instead of an all-or-nothing result. The upload form now accepts multiple files at once, and the source-files panel accepts drag-and-drop of one or more files, rejecting unsupported extensions client-side before any upload attempt. Added sort (upload date/name/status) and filter (status, file type) controls above the file list. No new backend endpoints were needed: every batch action is the frontend calling the existing single-file endpoint once per selected file and aggregating the results, so the existing single-file API tests already cover the underlying behavior; added Playwright coverage for the multi-file upload and partial-failure batch-archive flows.
- Fixed a stale Playwright test (`workspace.spec.ts`) that had been silently failing since the "name the file in the upload message" change earlier in Phase 10: it asserted the old generic "File uploaded and queued for processing." text, which the message no longer contains. Also fixed the same filename/status-text ambiguity (a locator matching both the status banner and the file row) surfacing in `full-workflow.spec.ts` and `phase9.spec.ts` once the richer batch messages were added.
- Reworked every multi-file batch message (upload, process, archive, restore, purge) into a short one-line summary (e.g. "2 of 4 file(s) uploaded and queued for processing, 2 failed.") plus a "Show details" toggle that expands a per-file breakdown grouped by outcome — Successful, Duplicate file, Not supported, and a generic Failed bucket for every other batch action — instead of inlining every failed filename and reason into the one-line banner, which didn't fit on one line once a batch had more than a couple of failures.
- Fixed drag-and-drop file rejections bypassing that same summary: the drop handler built its own separate raw message listing every client-side-rejected filename inline, so a mixed drop either showed the unsummarized list or lost it entirely once the upload's own message overwrote it a moment later. Also fixed an inconsistency found while verifying the fix: a validation rejection (400: unsupported type, too large, empty, invalid filename) was marked retryable, leaving the file stuck selected even though retrying would fail identically every time — only a genuinely transient failure (network error, 5xx) keeps a file selected now.
- Changed drag-and-drop from uploading immediately on drop to staging the dropped files the same way the file picker does (add to the pending selection, then require an explicit "Upload file(s)" click), so the two ways of adding files to the form behave identically instead of one committing immediately and the other requiring review first. Selecting or dropping files now also updates the status banner with a summary ("3 file(s) selected for upload." or, if a drop mixed in an unsupported extension, "2 file(s) selected for upload, 1 rejected (unsupported type).") and, for more than one file, a "Show details" breakdown listing each file's name and size — not a filesystem path, since browsers deliberately never expose one to a webpage for any file, however it was selected.
- Added a "Cancel" button next to "Upload file(s)," since staging now means a selection can sit there uncommitted with no way to back out of it otherwise. Clears the staged selection (from either the picker or a drop) without uploading anything and confirms in the status banner.
- Added a "Recent activity" panel that preserves the outcome of the last 5 completed multi-file batch actions (upload, process, archive, restore, purge), each with its own "Show details" breakdown, independent of the single-line status banner above it. Found via a real report: processing 26 files, then running a calculation before checking back, silently discarded the processing outcome — the batch doesn't block the rest of the page while it runs, and whichever action's status update lands last simply overwrites the banner with no way to recover what was there before. The banner itself is unchanged (still shows only the latest action); this panel is the durable record a long-running batch's result needed and didn't have.
