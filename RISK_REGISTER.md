# MVP Risk Register

| Risk | Impact | Mitigation | Status |
| --- | --- | --- | --- |
| Parser extraction is incomplete | Incorrect or missing site data | Preserve warnings/source references and expose failed status | Active |
| Missing or incorrect CRS | Incorrect geometry distances/areas | Require coordinate units, preserve CRS metadata, report transformation failures | Active |
| Calculations assume planar (projected) coordinates | If a project's CRS is geographic (lat/lon degrees), distance/area/perimeter formulas (Euclidean, via Shapely) would silently compute nonsense values labeled with the chosen linear unit, since degrees are not a linear measure | Found during the Phase 8 calculation review (VERIFY.md section 12); enforced 2026-09-19. `is_geographic_crs`/`ensure_projected_crs` (site_model.py, via pyproj) now reject a geographic CRS when a project tries to adopt one (422 on create/update), and again at measurement time for a project stored before that validation existed: distance/area/perimeter calculations return 400, a planar question returns the standard insufficient-data answer naming the CRS, and a site summary carries an attention flag. Slope and elevation statistics are untouched — they work on supplied numbers, not coordinate positions. An unknown or absent CRS still means "assume planar," as it always has. Regression tests: `test_geographic_coordinate_systems_are_detected_and_rejected`, `test_geographic_crs_is_rejected_and_never_measured_on_a_plane` | Mitigated (2026-09-19) |
| OCR is unavailable, affecting both TIFF uploads and scanned/image-only PDFs (a PDF page that is really just an embedded raster image with no text layer) | Raster plans provide metadata only for TIFF; a scanned PDF page produces a "Page N contains no extractable text" warning with nothing else extracted from that page | Defer OCR to the vision phase and show a warning; confirmed against real scanned PDFs (`DEST213523.pdf`, `Rinker_001.pdf`, `Rinker_062.pdf`) — each is a single page with zero extractable text and one embedded raster image. Retry these same files once OCR is implemented | Accepted limitation |
| AI could invent engineering facts | Unsafe or unauditable answers | Route computable questions to deterministic calculations and require provenance; refuse with an explicit insufficient-data/ambiguous response otherwise | Mitigated |
| Large or malformed uploads | Resource exhaustion or failed processing | 50 MB limit, MIME/extension validation, isolated failures | Mitigated |
| Accidental file deletion | Loss of source evidence | Archive files, preserve metadata, support restore and admin purge | Mitigated |
| Duplicate source files | Confusing project history | SHA-256 checksum detection within project, including archived records | Mitigated |
| Concurrent duplicate uploads | A race between the duplicate check and insert could let two identical files through | Database-level unique constraint on (project, checksum); the route treats the resulting integrity error as a duplicate-content conflict | Mitigated (Phase 8) |
| Local storage failure | Unavailable source documents | Document backup/restore and retain checksums/metadata | Mitigated (Phase Z, DEPLOYMENT.md) |
| Unauthenticated local API | Unauthorized access if exposed | Session-cookie auth with three roles (admin/power_user/user) and per-project ownership/membership enforced on every endpoint (ADR-009, PLAN.md Phase 15). As of 2026-09-19, Phase 15 is fully complete including its follow-up items: UI role-gating on every archive/purge/restore control (not just the top-level project archive), owner-vs-any-collaborator gating corrected to match what each backend route actually requires, an "Add collaborator"/"Reassign owner" UI, and Playwright e2e coverage for the auth layer (22/22 passing) | Mitigated (Phase 15, complete) |
| A real network-calling AI provider could hang or fail slowly | Slow or stuck requests once a live provider is connected | The current MockAIProvider makes no network calls; timeout/retry handling is deferred until a real provider (e.g. OpenAI) is integrated post-MVP | Deferred to post-MVP |
| Oversized or malicious request bodies | Resource exhaustion on non-upload endpoints | 2 MB request-body limit on non-multipart requests | Mitigated (Phase 8) |
| LandXML coordinate order varies by producer | The parser assumes the common "northing easting [elevation]" order; a file that instead uses "easting northing" would silently swap X/Y | Documented assumption in `extraction.py`; not detected or validated at parse time since there is no reliable in-file signal to distinguish the two orders | Open (Phase 9) |
| LandXML coordinate numbers may use a comma decimal separator (e.g. German-locale CAD exports) instead of a period | Every point in the file would fail to parse as a float, causing the whole file to be rejected as having no supported geometry even though it is well-formed | A coordinate token that fails standard `float()` parsing and contains exactly one comma with no period is reinterpreted with the comma as a decimal point; found via a real Vestra Cad Civil export | Mitigated |
| LandXML curved alignments (Curve/Spiral, and PI segments with a curve/spiral) are not extracted | Corridor/parcel geometry defined by arcs is invisible to the site model rather than approximated incorrectly | Explicit warning naming the skipped segment/PI transition; only straight Line and tangent-to-tangent PI segments are extracted, for both `CoordGeom`- and `AlignPIs`-style alignments | Accepted limitation (Phase 9) |
| A `pntRef` target that is never defined anywhere in the file | The referencing point/line endpoint can't be resolved to coordinates | Consolidated into a single warning listing up to 10 unresolved reference IDs, rather than one warning per occurrence (real files can reference the same missing point hundreds of times) | Accepted limitation |
| Label-to-geometry proximity linking used a fixed 10-unit cutoff | Not unit-aware: 10 ft and 10 m are very different distances, so the same constant could be too loose or too strict depending on the project's coordinate units | Fixed 2026-09-19: the cutoff is now a real-world distance (ten feet, `LABEL_LINK_MAX_DISTANCE_METERS` in routes.py) converted into each project's own coordinate units, read from the project's CRS via `crs_linear_unit_meters` when it has one and from its declared unit system otherwise. A foot-based project keeps the same ten-unit cutoff as before; a metre-based project now gets 3.048 units instead of ten. Regression test: `test_label_link_cutoff_is_expressed_in_the_project_s_own_coordinate_units`. `TIGHT_SETBACK_UNITS` in ai_service.py is still unit-agnostic — it is a heuristic attention flag, not a measurement, and is not covered by this fix | Mitigated (2026-09-19) |
| Label linking only covers DXF-sourced labels | PDF text is whole-page and TXT/CSV lines are aggregated, so neither carries the per-label coordinates needed to compute proximity | Accepted for this item; revisit once PDF/text extraction carries per-label positions | Accepted limitation (Phase 9) |
| Key-phrase vocabulary is a fixed, curated list | A phrase used in a real client document but absent from `KEY_PHRASES` in extraction.py (e.g. a jurisdiction-specific term) will not be surfaced as an annotation | Deterministic and easy to extend; not a learned/statistical extractor, so coverage is only as good as the list | Accepted limitation (Phase 9) |
| COGO bearing/distance parsing only covers CSV quadrant bearings | Only CSV input with explicit x/y (or easting/northing) plus bearing/distance columns is chained into geometry; DXF/LandXML bearing text (e.g. an annotated boundary call on a plan sheet) is not parsed into geometry, and azimuth or non-quadrant bearing formats are not recognized | Accepted for this item: CSV courses are the clearest, most tractable case since a point of beginning is unambiguous; DXF/LandXML COGO text lacks a reliable "previous point" reference to chain from | Accepted limitation (Phase 9) |
| Semantic entity classification is keyword-based, inferred only from a DXF layer name or an explicit CSV type/classification column | A parcel boundary drawn on an ambiguously-named layer (e.g. "L-1") or a CSV without a type column will not be classified; classification is never guessed from geometry shape alone | Deterministic and conservative by design (avoids inventing a classification with no textual evidence); coverage depends on how the source file names its layers/columns | Accepted limitation (Phase 9) |
| Directional questions depend entirely on semantic_type classification and only support four compass words | A direction+role question about an unclassified entity (no semantic_type) or a role outside parcel/building/driveway/curb-cut returns "insufficient data" instead of an answer; only "north/south/east/west" are recognized (no intercardinal directions like "northeast") | Accepted for this item: directional resolution is only as good as the classification it depends on (see the classification risk above) | Accepted limitation (Phase 9) |
| Plan-sheet snippets only cover DXF-sourced entities | PDF/CSV/TXT/LandXML entities return a 400 when a snippet is requested; PDF rasterization would need a new dependency (e.g. PyMuPDF) not currently in the project | Accepted for this item: DXF rendering is achievable with the already-installed ezdxf library's built-in SVG backend, so it was implemented without adding a dependency; PDF snippet support is deferred until that dependency decision is made | Accepted limitation (Phase 9) |
| A CSV row's `elevation` column was dropped when building its point geometry | `_table_row_point` in routes.py only read x/y, so elevation/slope questions and calculations could never work from CSV point data even when the source file had an elevation column | Found via the Phase Z final smoke test (2026-09-16): asking a slope question after uploading a two-point CSV with elevations returned "insufficient data". Fixed by also reading an elevation/z column and carrying it as the point's third (Z) coordinate; regression test added (`test_csv_point_elevation_is_kept_as_the_z_coordinate`) | Fixed (Phase Z, 2026-09-16) |
| Perimeter and area were not reachable from the natural-language question endpoint | `route_question` in ai_service.py recognized distance/setback, slope, elevation, and directional questions, but had no branch for "perimeter" or "area" — such a question fell through to the generic summary intent (which only looks for extracted text) and always reported insufficient data, regardless of what geometry was available | Found via the Phase Z final smoke test (2026-09-16). Fixed by adding `_answer_area`/`_answer_perimeter`, each resolving to a single Polygon/LineString entity (not `_answer_distance`'s "exactly two geometries" pattern, since perimeter sums every segment in a shape rather than measuring between two points) and calling the existing `calculate_area`/`calculate_perimeter` functions. Regression test: `test_area_and_perimeter_questions_are_routed_and_answered` | Fixed (2026-09-16) |
| `_answer_area`/`_answer_perimeter` don't filter candidates by the semantic role the question named | Unlike `_answer_directional`, neither filtered by `semantic_type` — a project with both a parcel boundary and a building footprint polygon made "What is the parcel area?" and "What is the building footprint area?" collide on the same candidate pool and return "ambiguous" instead of picking the one the question actually asked about | Found via a `PLAN.md` Phase 14 audit against `TestQuestions`, tracked as this phase's first work item; fixed 2026-09-19 by extracting `_question_role()` (shared with `_parse_directional_question`) and using it to narrow candidates in both functions before the ambiguity check, with no role phrase in the question leaving all candidates in play (unchanged prior behavior). Regression test: `test_area_and_perimeter_questions_pick_the_named_role_instead_of_colliding` | Fixed (2026-09-19) |
| Question-answering coverage gaps found via a `TestQuestions` audit (PLAN.md Phase 14) | Counts, building/lot dimensions and orientation, a building's setback clearance, and drainage/utility presence questions all fell through to the generic text-retrieval summary with no computed value, even where the underlying geometry/classification already existed | Fixed 2026-09-19: added semantic-type keywords for utility easement/parking/tree/sidewalk/detention basin (routes.py); a `count` intent; `dimensions`/`orientation` from a polygon's minimum-area oriented bounding rectangle; a `setback_compliance` intent measuring boundary-to-boundary clearance between a building footprint and its parcel (compliant/not-compliant only when the question states an explicit numeric setback with a unit, otherwise clearance alone); and `drainage`/`utility` intents wired to the existing `_keyword_summary` rollup. A role with zero classified entities returns insufficient data, never an affirmative zero. Not done: a generic "where is the X located" lookup for an arbitrary role (only count/presence), and document title-block metadata (project name, sheet number, scale, etc.) — both remain open in PLAN.md Phase 14. Regression tests: `backend/tests/test_qa_coverage_expansion.py` | Mitigated (Phase 14, 2026-09-19) |
| `_parse_directional_question` matched compass words as a bare substring | `"east"` is a substring of ordinary English words like "least" — any threshold-style question containing "at least" (e.g. "at least 25 ft") was misdetected as asking about compass east, and "northeast"/"southwest"-style intercardinal phrasing was silently misread as one of the four supported cardinal directions rather than falling through | Found while adding the `setback_compliance` intent above, whose natural phrasing ("is the building's setback at least 25 ft") triggered it. Fixed with `\b`-bounded regex matching instead of `in`. Regression test: `test_directional_parsing_does_not_misfire_on_east_as_a_word_fragment` | Fixed (2026-09-19) |
| Tenant query-scoping has no database-enforced backstop yet | PLAN.md Phase 16 (DECISIONS.md ADR-010) added the `Tenant` schema, a `platform_admin` role, and app-layer query scoping: `admin` now sees/manages only its own tenant's projects/clients/users (`is_project_member`/`is_project_owner` and everything depending on them, `list_projects`/`list_archived_projects`/`list_clients`/`list_users`/`list_archived_files`/`list_purge_history`, and every cross-tenant reference at write time), while `platform_admin` still crosses every tenant. This is app-layer-only, the same convention used everywhere else in this codebase — but the original multi-tenant study judged app-layer scoping alone insufficient for this severity class (a missed filter is a cross-*customer* leak, not a contained permission bug) and recommended Postgres Row-Level Security as a second, database-enforced line of defense. That backstop does not exist yet | App-layer scoping shipped 2026-09-20, verified against two seeded tenants (`backend/tests/test_tenant_isolation.py`, 8 tests, confirmed real via a revert-and-recheck on the core check) with zero behavior change for a dedicated (single/no-tenant) install (all 134 pre-existing tests unchanged). Still open: Row-Level Security as the recommended backstop before running a real shared instance, per-tenant `username` uniqueness (still a global uniqueness check), and an actual tenant-provisioning API (a `platform_admin` can only target an *existing* `Tenant` row today) | Open (Phase 16, 2026-09-20) |
